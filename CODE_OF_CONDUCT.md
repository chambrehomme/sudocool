# Team Charter & Code of Conduct

> **Project:** sudocool
> 
> **Repository:** [sudocool](https://github.com/chambrehomme/sudocool.git)

## Overview & Goal

This document defines how we collaborate on our sudocool project.

As a personal hobby project, our primary focus is combining our shared interests in Sudoku and
software engineering. We aim to enjoy the development process, experiment with new technologies.

Our goal is not only to build a functional Sudoku app, but also to make it enjoyable, well-designed,
and technically interesting, while exploring our own ideas and preferences along the way.

## Principles

### Core Principles

> **Build something we would enjoy using**:
>
>The app should reflect our own ideas about what makes a good Sudoku app.

> **Keep it simple**
>
>We avoid unnecessary complexity and features that do not provide value.

> **Quality over quantity**
>
> We would rather have a smaller number of well-designed features than a large number of features
> that
> make the app unnecessarily complicated.

> **Have fun**
>
>This is a hobby project. Enjoying the process is an important part of the project.

### Learning & Experimentation

One of the main purposes of this project is to learn and experiment.
Therefore, we explicitly encourage:

* Trying new technologies
* Exploring different architectural approaches
* Prototyping ideas
* Refactoring when we discover better solutions
* Learning from failed approaches
* Using pair programming to share knowledge and learn from each other

## Organization & Workflow

Since this is a passion project, we do not follow a strict agile framework. We organize our work
flexibly around our available free time.

### Communication & Meetings

* **Meetings:** Conducted on an ad-hoc basis for brainstorming, technical alignment, and
  problem-solving.
* **Decisions:** Day-to-day coordination happens informally, but major technical/architectural
  decisions are documented directly on GitHub.

### GitHub Project Board

We use GitHub Projects to organize and track our work.

The project board consists of the following columns:

| Column      | Description                                                  |
|:------------|:-------------------------------------------------------------|
| **Backlog** | Ideas, features, and tasks that we may work on in the future |
| **Ready**   | Tasks that are clearly defined and ready to be started       |
| **Doing**   | Tasks currently being worked on                              |
| **Review**  | Tasks completed and awaiting review, feedback, or approval   |
| **Done**    | Tasks that are finished, approved, and fully completed       |

The board is kept lightweight and is mainly used to give us an overview of what we are working on
and what we want to do next.

## Quality Understanding & Git Rules

### Definition of Done (DoD)

An issue or PR is considered **done** when:

- [ ] Code is reviewed and approved by the non-authoring team member
- [ ] Code is clean, maintainable, understandable and merged into `main` branch
- [ ] All relevant tests pass successfully
- [ ] Documentation is created or updated

### Git Conventions

* **Branching Strategy:** Feature branches
* **Branch Naming:** `feature-<issue-nr>-<short-description>` or
  `docs-<issue-nr>-<short-description>` or `bug-<issue-nr>-<short-description>`
* **Commit Messages:** [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)
* **Pull Request Rules:** 1 approval required, all comments resolved, branch up-to-date
* **Who may merge:** Any team member after successful review

### Issue Labels

* **epic**: Overarching project goals that are broken down into features
* **feature**: A vertically-scoped feature of the project that is broken down into stories
* **story**: A user story of the project, scoped to a single component
* **documentation**: Documentation of the project
* **testing**: Testing of the project
* **bug**: Bug in the project that needs to be fixed

## Code of Conduct

We are committed to:

* Respectful and open communication
* Active participation in meetings and teamwork
* Reliability in deliveries and agreements
* Transparency about problems or delays (communicate early)
* Constructive criticism (we criticize ideas, not people)
* Punctuality at meetings
* Supporting team members when they face difficulties

We do not accept:

* Personal attacks or disrespectful behavior
* Discrimination of any kind
* Ignoring messages
